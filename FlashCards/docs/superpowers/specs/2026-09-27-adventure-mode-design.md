# Adventure Mode — Design Spec

**Date:** 2026-09-27
**Status:** Approved for implementation
**Working name:** Adventure (in-fiction: the Victor region)

This spec fixes the design, the architecture, the data formats, the battle math and the retro feel, and indexes every work item. The task-by-task plans with the complete test-first code live beside it:

- `docs/superpowers/plans/2026-09-27-adventure-m1-gym-circuit.md`
- `docs/superpowers/plans/2026-09-27-adventure-m2-overworld.md`

## 1. Vision and player loop

**How to use this plan.** Every work item below is one red-green-refactor cycle of under a day: write the listed tests first and watch them fail to compile or fail to pass (red), write the smallest implementation that makes them pass (green), then tidy names and extract functions with the tests still green (refactor). Each work item states a `Goal`, its `Files`, its `Tests` with what each asserts, an `Implementation` note describing the minimal green step, and a `Done` criterion. Work items are numbered `M1-01` style so reviews and commits can reference them. New code carries no comments of any kind, not even `///` doc comments or `// MARK:` lines; intention-revealing names, small functions and the test names carry the meaning. Pure logic goes in the `IFRCore` package and runs on Linux with `scripts/test-core.sh`; only rendering, persistence, notifications and haptics live in the app and need Xcode. Section 7 says which tests run where.

**The loop.** Adventure is the fifth tab. Opening it shows a Game Boy Advance screen: a 240 by 160 pixel canvas scaled to an exact integer multiple, letterboxed in `Theme.panel`, every pixel a crisp square. The picture is an enroute chart drawn as a Pokemon region: eight airports are towns, blue Victor airways join them, and cloud banks are the tall grass where wild questions hide. A dialogue box types out one character at a time in Press Start 2P: "Welcome to the Victor region. Dr. Hypoxia is waiting at KHYP." A triangle cursor blinks until you tap.

Each airport hosts a gym for one of the eight `IFRCore.Category` cases in the fixed order Human Factors (Dr. Hypoxia), Instruments & Systems (Gyro), Regulations (Marshal Reg), Navigation (Victor), Charts & Planning (Plotter), Weather (Nimbus), Emergencies (Mayday), Approaches (Ilsa). Tap the next unlocked airport, read two lines of leader taunt, tap `Challenge`, the screen flashes white and wipes into battle. Your companion sits bottom-left with an HP bar; the leader's creature sits top-right with its own. A question types into the dialogue box; the answer options appear below the screen as a move menu. Answer right and the enemy bar ticks down, with "It's super effective!" on a difficulty-3 question and "A critical hit!" when you answered within six seconds of the options appearing. Answer wrong and the screen shakes, your bar drains, and the explanation types out so a miss always teaches. The leader's HP is tuned from the ten questions actually drawn so that seven correct wins and six never does, the same 70 percent bar as `QuizScore.passed`. Win and a badge fanfare lights the airport; lose and the box says "You whited out... Your misses come back sooner." Both are true statements about the scheduler, because every answer went through `Grade(mcCorrect:)` and the same `StudyStore` review path as the Study and Quiz tabs: a first-ever miss lands in tomorrow's queue, and a miss on a well-known card shortens its interval through `Scheduler.review` (a card with six `.good` reviews behind it comes back in about two weeks instead of months).

Eight badges open the Elite Four, four mixed-category gauntlets fought back to back with only a partial heal between them. Beating them opens the Champion, who is the existing 60-question exam-weighted mock exam wearing a cape: all sixty questions are answered, the bars show 42 and 19, and the verdict is `QuizScore.passed`.

Milestone 2 makes the region walkable: tap-to-walk on a 40 by 30 tile map with A-star paths, cloud tiles that roll one-question wild encounters drawn due-first from the study queue, trainers who spot you down an airway, items that only touch HP or movement, and a rival who always brings your weakest categories. Milestone 3 adds one companion per category with three evolution stages tied to `MasteryLevel`, rematch notifications when a badge's category retention decays, a Battle Tower survival mode and link battles from a shared quiz seed. Nothing in any milestone can fake mastery.

## 2. Architecture

All game rules live in a new folder `IFRCore/Sources/IFRCore/Adventure/` as pure, `Sendable`, deterministic value types. Randomness enters only as `inout some RandomNumberGenerator` (tests pass `SeededRNG(seed:)`), time only as `now: Date`, `answerSeconds: Double` or a frame index. Nothing under `Sources/IFRCore` imports UIKit or SwiftUI, and a grep test enforces it. The app layer under `App/Screens/Adventure/` turns `PixelFrame`s into images, measures wall-clock, and persists one Codable blob. Every renderer that produces a `PixelFrame` from engine values lives in IFRCore too, so the app never composes pixels.

### 2.1 IFRCore: Adventure/Battle

- `Hit: Equatable, Sendable` with `amount: Int`, `isCritical: Bool`, `isSuperEffective: Bool`.
- `enum Damage { static func hit(difficulty: Int, answerSeconds: Double) -> Hit }`. Integer percent math, no floating point.
- `enum PlayerHP { static func maximum(for level: MasteryLevel) -> Int }`.
- `enum OpponentHP { static func tuned(for questions: [Question], passMarkPercent: Int = 70) -> Int; static func cloud(for question: Question) -> Int }`. `cloud` returns `Damage.hit(difficulty: question.difficulty, answerSeconds: 10).amount`, so a cloud has 8, 10 or 12 HP and any correct answer knocks it out.
- `enum BattleTier: String, Codable, Sendable { case cloud, trainer, gym, eliteFour, tower, link, champion }`, declared in exactly that order with `champion` last, with `var missDamage: Int` (the floor-1 value for tower), `var runsEveryQuestion: Bool` (true only for champion) and `func damage(for hit: Hit) -> Int` (1 for champion, `hit.amount` otherwise).
- `Opponent: Equatable, Codable, Sendable` with `id`, `name`, `nameplateName` (at most 7 characters, uppercase ASCII), `spriteID`, `tier`, `maxHP`, `gymID: GymID?` and `airportID: String?` (both nil for every tier except `.gym`). `Gym.opponent(maxHP: Int, airportID: String) -> Opponent` is the only mapping from JSON gym to opponent: `id = gymID.rawValue`, `name = leaderName`, `spriteID = leaderSpriteID`, `tier = .gym`, `gymID` and `airportID` filled. `BattleResolution` reads those two fields and never looks a gym up by name.
- `BattleState: Equatable, Codable, Sendable` with `opponent`, `deck: [Question]`, `cursor: Int`, `playerHP`, `playerMaxHP`, `opponentHP`, `missDamage: Int`, `reviveArmed: Bool`, `results: [Bool]`, `turns: [BattleTurnResult]`, `outcome: BattleOutcome?`, `var currentQuestion: Question?`. It is never persisted; leaving a battle forfeits it.
- `BattleTurnResult: Equatable, Codable, Sendable` with `questionID`, `selectedIndex`, `isCorrect`, `grade: Grade`, `hit: Hit?`, `damageToPlayer: Int`.
- `enum BattleOutcome: Equatable, Codable, Sendable { case won, lost }`.
- `enum BattleEvent: Equatable, Sendable { case questionPresented(Question), opponentHit(Hit, damage: Int), playerHurt(Int), explanation(String), revived(Int), opponentFainted, playerFainted, deckExhausted }`.
- `enum BattleEngine { static func start(opponent: Opponent, deck: [Question], playerMaxHP: Int, missDamage: Int? = nil) -> BattleState; static func answer(_ state: BattleState, selectedIndex: Int, answerSeconds: Double) -> (state: BattleState, events: [BattleEvent]); static func forfeit(_ state: BattleState) -> (state: BattleState, events: [BattleEvent]); static func useItem(_ state: BattleState, effect: ItemEffect) -> BattleState }` (`useItem` arrives in M2-06). `missDamage` defaults to `opponent.tier.missDamage`; the tower passes `BattleTower.missDamage(floor:)`. The exact event array for every answer case is fixed in section 4 (Turn event order).
- `enum BattleTuning { static func totalBaseDamage(of: [Question]) -> Int; static func winsWithoutCriticals(deck: [Question], correctIndices: Set<Int>) -> Bool; static func winsWithCriticals(deck: [Question], correctIndices: Set<Int>, criticalIndices: Set<Int>) -> Bool }` for tests only.
- `EliteFourRun: Equatable, Sendable` with `memberIndex`, `playerHP`, `playerMaxHP`, `var isCleared: Bool` (`memberIndex == 4`); `static func start(playerMaxHP:) -> EliteFourRun`; `func advancing(after battle: BattleState) -> EliteFourRun?` (nil on a loss; after the fourth win returns a run with `isCleared == true`); `static func carryOverHP(current: Int, max: Int) -> Int` heals 30 percent of max, capped. The run is in memory only: leaving the app or the screen abandons it and the next attempt starts at member one.
- `enum ChampionBattle { static let opponentHP = 42; static let playerHP = 19; static func deck(bank:states:scheduler:now:using:) -> [Question]; static func outcome(results: [Bool]) -> BattleOutcome }`. `deck` calls `QuizEngine(scheduler:).makeQuiz(config: .mockExam, bank:states:now:using:)`; `outcome` returns `.won` exactly when `QuizEngine.score(results:).passed`.

### 2.2 IFRCore: Adventure/Encounters

`EncounterDeck: Sendable` with `init(scheduler: Scheduler)` and `func draw(count: Int, categories: [Category]?, bank: QuestionBank, states: [String: CardState], now: Date, using rng: inout some RandomNumberGenerator) -> [Question]`. It takes no `StudySettings` and no `newIntroducedToday`, because the due-first prefix contains due cards only.

The draw rule, stated once so every caller and test agrees:

1. `categories` is an ordered list in circuit order, or nil for one pool over the whole bank. With `n` categories, `count` is split evenly: `count / n` each, remainder to the earliest. Twelve over two gives 6 and 6; six over three gives 2 each; ten over one gives 10.
2. For each category quota, the due-first prefix is `StudyQueue.session(bank:states:settings: StudySettings(newCardsPerDay: 0), newIntroducedToday: 0, now:)` filtered by `isMultipleChoiceCapable` and that category, taken in queue order. With a zero allowance the queue holds only due cards (`reps > 0 && due <= now`), so the prefix never contains an unseen card. Within one category the queue is oldest-due first; with nil `categories` the queue's own round-robin-by-category order (categories sorted by `Category.rawValue`, oldest-due first within each) is kept as is. The `settings.unlockedCategories` gate is dropped explicitly: it only filters the queue's new cards, which the prefix never takes, and a due card in a locked category keeps its schedule in the Study tab too, so it draws here as well. `newCardsPerDay` never applies to a draw; unseen cards enter only through the top-up in step 3.
3. The remainder of the quota is topped up with `QuizEngine.makeQuiz(config: QuizConfig(category: c, length: remaining, isMockExam: false), bank: bankExcludingChosen, states:, now:, using: &rng)` where `bankExcludingChosen` is `QuestionBank(version:questions:)` minus every id already chosen. `makeQuiz` weights unseen cards 1.25 and never pads, so the top-up may contain unseen cards and the draw may come back short.
4. A nil `categories` runs steps 2 and 3 once with `category: nil`, keeping the round-robin order of step 2 for the prefix.

Every question answered in Adventure that has no `CardStateRecord` yet is inserted by `applyReview` with `introducedOn = now`, so Adventure consumes the Study tab's new-card allowance for the day; that is deliberate, the card really was introduced. This is the only drawer for gyms, trainers, Elite Four members, clouds, the rival and the tower. The Champion uses `ChampionBattle.deck`; link battles use `LinkBattleCode.deck`, which is `makeQuiz` with empty states.

### 2.3 IFRCore: Adventure/Content

- `AdventureContent: Codable, Sendable` with `version`, `region: RegionMap`, `gyms: [Gym]`, `eliteFour: [EliteMember]`, `champion: ChampionSpec`, `dialogue: [String: DialogueScript]`, `system: [String: DialogueScript]`, `items: [Item]`, `tileMap: TileMap?`, `trainers: [Trainer]`, `rival: RivalSpec?`, `companions: [CompanionSpecies]`; `static func load() throws -> AdventureContent` (reads `Resources/adventure-v1.json` through `Bundle.module`, decodes with a plain `JSONDecoder`, then calls `validate()`); `func validate() throws`. Optional and array fields default to nil or empty through `decodeIfPresent`, so the Milestone 1 file ships without overworld or companion content.
- `enum AdventureContentError: Error, Equatable, Sendable { case resourceMissing, duplicateID(String), gymOrderMismatch, unknownReference(from: String, to: String), emptyDialogue(String), dialoguePageTooLong(String), nameplateTooLong(String), unknownSprite(String), notEnoughQuestions(gymID: String), offMap(String), unknownTile(x: Int, y: Int), raggedRows, unreachableDoor(airportID: String) }`.
- `RegionMap { airports: [Airport]; airways: [Airway] }`, `Airport { id; name; position: GridPoint; gymID: GymID?; role: AirportRole }` with `AirportRole { gym, eliteFour, champion, waypoint }`, `Airway { id; from; to }`. `position` is a cell on the 30 by 14 region grid of 8-pixel cells above the dialogue box; `x >= 30` or `y >= 14` throws `.offMap(airportID)`.
- `Gym: Codable { id: GymID; leaderName; nameplateName; leaderSpriteID; badgeName; questionCount; dialogue: DialogueRefs }`, `DialogueRefs { intro; win; lose }`, `EliteMember { id; order; name; nameplateName; spriteID; categories: [Category]; questionCount; dialogue: DialogueRefs }`, `ChampionSpec { name; nameplateName; spriteID; dialogue: DialogueRefs }`, `DialogueScript { pages: [String] }`. Every `nameplateName` longer than 7 characters throws `.nameplateTooLong(id)`.
- `enum SystemDialogueKey: String, CaseIterable, Sendable { case welcome, gymLocked, victory, whiteout, retreat, championPinned, superEffective, criticalHit, revived }` names every string the app shows in the box that is not authored per opponent; `system` must contain each key or `validate()` throws `.unknownReference(from: "system", to: key)`. `enum DialogueTemplate { static func filled(_ script: DialogueScript, with values: [String: String]) -> DialogueScript }` replaces the placeholders `{badge}`, `{leader}`, `{airport}` and `{opponent}`; `AdventureContent.systemLine(_ key: SystemDialogueKey, filling values: [String: String] = [:]) -> DialogueScript` is the only reader. Validation fills every system page with the longest badge name, leader name, airport id and opponent name in the content and requires the result to paginate to one page, else `.dialoguePageTooLong(key)`.
- `Item { id; name; spriteID; effect: ItemEffect }` and `enum ItemEffect: Codable, Equatable, Sendable { case heal(Int), reviveOnce, repel(steps: Int), directTo }` decoded from `{"kind": ..., "amount": ...}`; any other `kind` throws on decode. There is no effect that can reach a question, a deck, a grade or a card state.
- `TileMap`, `Trainer`, `RivalSpec` (M2) and `CompanionSpecies` (M3) are described in section 3.

### 2.4 IFRCore: Adventure/Circuit

- `enum GymID: String, Codable, CaseIterable, Sendable { case humanFactors, instrumentsAndSystems, regulations, navigation, chartsAndPlanning, weather, emergencies, approaches }` declared in circuit order; `var category: Category`; `var next: GymID?`; `var previous: GymID?`.
- `AdventureSave: Codable, Equatable, Sendable`, the single persisted value. Milestone 1 fields: `saveVersion: Int = 1`, `badges: Set<GymID>`, `badgeQuestionIDs: [String: [String]]` (keyed by `GymID.rawValue`, the ids of the questions in the winning draw), `eliteFourCleared: Bool`, `championWins: Int`, `hallOfFame: [Date]`, `battlesWon`, `battlesLost`, `visitedAirportIDs: Set<String>`. Milestone 2 appends `defeatedTrainerIDs: Set<String>`, `collectedItemIDs: Set<String>`, `inventory: [String: Int]`, `repelStepsLeft: Int`, `position: GridPoint?`, `facing: Direction?`, `rivalEncountersDone: Set<Int>`. Milestone 3 appends `seenCompanionStages: [String: Int]` (keyed by `Category.rawValue`), `bestTowerFloor: Int`, `lastRematchNotice: Date?`. Custom `init(from:)` uses `decodeIfPresent` per field with a default, `static let new`, and every milestone that appends a field names a decoding test for a blob without it. `static let currentVersion = 1` is the version this build writes. Decoding a blob whose `saveVersion` is greater than `AdventureSave.currentVersion` throws `AdventureSaveError.newerThanApp(Int)`; the store then works from `.new` in memory and never overwrites the blob.
- `enum AdventureSaveError: Error, Equatable, Sendable { case newerThanApp(Int) }`, thrown only from `AdventureSave.init(from:)` and carrying the offending `saveVersion`.
- `enum CircuitRules { static func isUnlocked(_ gym: GymID, save: AdventureSave) -> Bool; static func isEliteFourUnlocked(save:) -> Bool; static func isChampionUnlocked(save:) -> Bool }`. After clearing, both the Elite Four and the Champion stay unlocked and are re-challengeable independently; a Champion rematch never requires re-clearing the Elite Four.
- `enum BattleResolution { static func apply(_ outcome: BattleOutcome, opponent: Opponent, deck: [Question], to save: AdventureSave, at date: Date) -> AdventureSave }`. A gym win inserts `opponent.gymID` into `badges`, records the deck ids under `badgeQuestionIDs[gymID.rawValue]`, inserts `opponent.airportID` into `visitedAirportIDs`; an Elite Four win only counts the battle, because clearing is decided by `EliteFourRun.isCleared` through `StudyStore.finishEliteFourRun`; a champion win appends to `hallOfFame`.
- M3: `enum RematchAdvisor { static func gymsAtRisk(save: AdventureSave, categoryRetention: [GymID: Double], badgeQuestionRetention: [GymID: Double], threshold: Double = 0.6) -> [GymID] }`. A badged gym is at risk when either its coverage-aware category retention (section 2.8) or the mean retrievability of its `badgeQuestionIDs` is at or below the threshold; unbadged gyms never are; the result is sorted by the lower of the two numbers ascending, so the first element is the gym most in need of a rematch.
- M3: `RematchNotice: Equatable, Sendable { gym: GymID; leaderName: String; badgeName: String; airportID: String }` with `static func notice(for gym: GymID, content: AdventureContent) -> RematchNotice?` (nil when no airport carries that gym). The app builds these from content and hands them to `NotificationScheduler`, which never sees `AdventureContent`.

### 2.6 IFRCore: Adventure/Overworld (Milestone 2)

- `GridPoint: Hashable, Codable, Sendable { x, y }`, `enum Direction: String, Codable { up, down, left, right }` with `delta` and `opposite`.
- `enum TileKind: Character { ground = ".", airway = "=", cloud = "~", water = "w", terrain = "#", building = "B", door = "D", sign = "S" }` with `isWalkable` and `blocksSight`; `TileMap` (section 3) with `subscript(GridPoint) -> TileKind?`.
- `enum Pathfinder { static func path(from: GridPoint, to: GridPoint, in map: TileMap, blocked: Set<GridPoint>) -> [GridPoint]? }`. A-star, four-connected, Manhattan heuristic. The open set is ordered by `(f, h, y, x)` ascending and popped from the front; neighbours are expanded in the order up, right, down, left; the closed set is keyed by `GridPoint`; a node already in the open set is replaced only when the new `g` is strictly lower. `blocked` is the set of positions of undefeated trainers and nothing else; a rival encounter tile is an ordinary walkable tile, so a path can reach it. The returned path excludes the start and includes the goal.
- `OverworldState: Codable, Equatable { position; facing; pendingPath: [GridPoint]; stepsSinceEncounter: Int; suppressedTrainerID: String? }` with `func stepping(_ direction: Direction, in map: TileMap, blocked: Set<GridPoint>) -> (OverworldState, OverworldEvent)` (a step into terrain, water, a building or a `blocked` tile only turns, so the D-pad and tap-to-walk obey the same walls), `func targeting(_ goal: GridPoint, in map: TileMap, blocked: Set<GridPoint>) -> OverworldState` (a tap on a non-walkable or unreachable tile leaves `pendingPath` unchanged; a tap on the player's own tile clears it), `func interrupted() -> OverworldState` (clears `pendingPath`), and `enum OverworldEvent { none, blocked, warp(String), sign(String), pickup(String), cloud }` where `warp` carries an airport id. `stepping` only moves, turns and reports the tile; it never rolls, never sees the save and never touches `stepsSinceEncounter`.
- `enum OverworldOutcome: Equatable, Sendable { case none, blocked, warp(String), sign(String), pickup(String), encounter(category: Category), sighted(Trainer), rival(encounterIndex: Int) }` and the one per-step reducer the screen calls: `enum OverworldTurn { static func advancing(_ state: OverworldState, direction: Direction, save: AdventureSave, map: TileMap, trainers: [Trainer], rival: RivalSpec?, using rng: inout some RandomNumberGenerator) -> (state: OverworldState, save: AdventureSave, outcome: OverworldOutcome) }`. In order: it builds `blocked` from `trainers` minus `save.defeatedTrainerIDs` and calls `stepping`; on a moved step it decrements `save.repelStepsLeft` toward zero; on a cloud step with no repel it increments `stepsSinceEncounter` (no increment while repelled), on a non-cloud step it resets the counter to zero; it calls `EncounterRoll.triggers` and on a trigger resets the counter and returns `.encounter(category:)` with the area's category; otherwise `RivalPlanner.pendingEncounter` decides `.rival`; otherwise `LineOfSight.trainerSeeing` decides `.sighted`, skipping `suppressedTrainerID`, which clears when that trainer no longer sees the player; `.pickup` runs `Inventory.adding` and inserts into `collectedItemIDs`; `.warp` and `.sign` pass through. On `.encounter`, `.rival` and `.sighted` the returned state has an empty `pendingPath`. The screen model calls only this function per step. The pity counter forces an encounter on the 24th consecutive cloud step.
- `enum Respawn { static func placement(save: AdventureSave, map: TileMap) -> (position: GridPoint, facing: Direction) }`: after any loss that did not come through a door (cloud, trainer, rival) the player is placed on the door tile of the nearest visited airport by Manhattan distance from `save.position`, or on `map.spawn` when none is visited, facing down; HP is never persisted. A trainer that beat the player becomes `suppressedTrainerID`, so the sighting cannot fire again until the player leaves and re-enters its sight line.
- `enum Camera { static func origin(following: GridPoint, mapWidth:mapHeight:viewportWidth: Int = 15, viewportHeight: Int = 10) -> GridPoint }`.
- `enum EncounterRoll { static let oneIn = 8; static let pityStep = 24; static func triggers(on tile: TileKind, repelStepsLeft: Int, stepsSinceEncounter: Int, using rng: inout some RandomNumberGenerator) -> Bool }`. The roll runs on every step that lands on a cloud tile, not only on entering cloud. Repel suppresses both the roll and the pity counter.
- `enum LineOfSight { static func trainerSeeing(_ player: GridPoint, trainers: [Trainer], defeated: Set<String>, in map: TileMap) -> Trainer? }` and `enum TrainerApproach { static func position(from start: GridPoint, toward player: GridPoint, step: Int) -> GridPoint }` (one tile per step along the facing line, never past the tile adjacent to the player). Trainer positions are not persisted; a trainer returns to its JSON position after the battle, and a trainer who beat the player stays in place but is suppressed as described under `Respawn`.
- `enum Inventory { static func adding(_ itemID: String, to save: AdventureSave) -> AdventureSave; static func using(_ itemID: String, from save: AdventureSave) -> AdventureSave? }` and `enum DirectTo { static func targets(save: AdventureSave, region: RegionMap) -> [Airport]; static func destination(of airport: Airport, in map: TileMap) -> GridPoint? }`: `targets` is the region's airports whose id is in `visitedAirportIDs`, in region order; `destination` is that airport's door tile from `map.warps`. The Direct-To picker lists exactly `targets`.
- `enum RivalPlanner { static func weakestCategories(count: Int, retention: [Category: Double]) -> [Category]; static func pendingEncounter(at position: GridPoint, spec: RivalSpec, save: AdventureSave) -> Int? }`. `pendingEncounter` returns the index of the first encounter whose `at` is the player's tile or four-adjacent to it, whose `afterBadges` is met and whose index is not in `rivalEncountersDone`; the rival tile is never in `blocked`, so both input paths can reach it.

### 2.7 IFRCore: Milestone 3

## 4. Battle math

All damage is integer arithmetic; the only rounding is one round-up in `OpponentHP.tuned`.

**Hit damage (correct answer).** `Hit.amount = 8 * difficultyPercent * criticalPercent / 10_000` with `difficultyPercent` 100, 125, 150 for difficulty 1, 2, 3 and `criticalPercent` 150 when `answerSeconds < 6`, else 100. Results: 8, 10, 12 normally; 12, 15, 18 on a critical. `isSuperEffective = difficulty == 3`. The app measures `answerSeconds` from the moment the last stem page finishes typing and the options become tappable, so long stems and slow dialogue never cost a crit. A fast wrong answer still costs HP and still grades `.again`; crits multiply damage and never touch the grade.

**Miss damage (wrong answer).** Flat per tier: cloud 20, trainer 30, gym 30, eliteFour 30, tower `20 + 5 * (floor - 1)`, link 30, champion 1 (see below). Difficulty and speed never reduce it.

**Player HP.** `PlayerHP.maximum(for: level) = 100 + 10 * (level.rawValue - 1)`: novice 100, apprentice 110, competent 120, proficient 130, instrumentMaster 140. Every battle starts at full HP. The level is `store.adventureMastery(for: gym.category).level` for gyms, trainers and clouds in that category (the coverage-aware `reviewedRetention` from section 2.8), and `MasteryLevel.level(forRetention:)` of the mean of `reviewedRetentionByCategory()` for mixed battles (Elite Four, tower, link, rival). The Champion ignores `PlayerHP.maximum` entirely and uses `ChampionBattle.playerHP` (19), because its bars are the mock exam's pass and fail counts. At 30 miss damage, novice through competent fall on the fourth miss and proficient and instrumentMaster fall on the fifth; four misses in a ten-question gym is already a lost 70 percent, so HP decides how early a bad run ends and never lowers the bar.

**Opponent HP.** `OpponentHP.tuned(for: deck) = (totalBaseDamage * 70 + 99) / 100`, computed over the concrete drawn deck with no criticals. Ten difficulty-2 questions give 70. The typical gym draw of three difficulty-1, four difficulty-2 and three difficulty-3 questions gives 24 + 40 + 36 = 100 and HP 70. Six correct without crits deal at most 36 + 30 = 66 and never win; seven correct win in 80 of the 120 possible subsets (67 percent) without crits; with one crit on any correct answer, seven correct win every subset except the one that misses all three difficulty-3 questions (24 + 40 = 64, plus at most 5 from one difficulty-2 crit = 69), so 119 of 120; with two crits seven correct always win (the smallest two-crit bonus is 4 + 4 = 8, and 64 + 8 = 72); eight correct always win. A difficulty-skewed draw therefore still demands 70 percent. Cloud opponents use `OpponentHP.cloud(for:)`, the base damage of their single question (8, 10 or 12), so any correct answer knocks them out; `OpponentHP.tuned` would give 6, 7 or 9 and is not used for clouds. Against the real bank the whole-category mean base damage is 9.97 (navigation) to 10.38 (humanFactors), so 70 HP equals 6.75 to 7.02 average correct answers; a Linux test pins that band so bank edits cannot drift the tuning.

**Battle end.** After each answer: opponent HP at or below zero wins; else player HP at or below zero loses, unless `reviveArmed` is set, in which case HP is restored to `playerMaxHP / 2`, the flag clears and `.revived` is emitted instead of `.playerFainted`; else deck exhausted with the opponent standing loses ("you retreat to the FBO"). The champion tier ignores these rules. `BattleEngine.forfeit` sets `.lost` and emits `.playerFainted` from any unfinished state; `answer` after an outcome is a no-op. Reviews already submitted before a forfeit stand, because each one went through the store as it happened.

**Turn event order.** `BattleEngine.answer` returns the events of one answer in this fixed order, and the screen consumes them in sequence: correct with the opponent still standing gives `[.opponentHit(hit, damage:), .questionPresented(next)]`; correct and the opponent at or below zero gives `[.opponentHit(hit, damage:), .opponentFainted]` with outcome `.won`; wrong with the player still standing gives `[.playerHurt(missDamage), .explanation(text), .questionPresented(next)]`; wrong and fatal with `reviveArmed` gives `[.playerHurt(missDamage), .revived(playerMaxHP / 2), .explanation(text), .questionPresented(next)]`; wrong and fatal without a revive gives `[.playerHurt(missDamage), .explanation(text), .playerFainted]` with outcome `.lost`; the last question answered with the opponent standing gives the hit or hurt event, `.explanation` on a miss, then `.deckExhausted` with outcome `.lost`. The Champion emits `.opponentHit` or `.playerHurt` with damage 1 (damage 0 once that bar is pinned at zero), `.explanation` after every miss, `.questionPresented` until the sixtieth answer, and then `.opponentFainted` or `.playerFainted` from `ChampionBattle.outcome`. M1-03 asserts one array per case.

**Battle phases.** `BattlePhase` moves forward only, and the frame index restarts at 0 on every change. `wipe` (40 frames, `BattleWipe`) leads to `intro` (12 frames of `BattleIntro`, then the opponent's intro `DialogueScript` types and a tap on its last page advances) and then to `asking`. In `asking` the stem types page by page; the options become enabled and the answer clock starts when the last stem page is complete; tapping an option calls `BattleEngine.answer`, then `store.submitAdventureAnswer`, then enters `resolving`. In `resolving` the event array is consumed in order: `.opponentHit` and `.playerHurt` tick the bar to its target at 2 frames per HP while the hit sprite shakes and the `superEffective` or `criticalHit` system line types when the hit says so; `.explanation` types its pages and waits for a tap on the last; `.revived` types the `revived` line. A trailing `.questionPresented` returns to `asking`; a trailing `.opponentFainted`, `.playerFainted` or `.deckExhausted` enters `ended`. In `ended` the victory or defeat animation plays, then the `victory`, `whiteout` or `retreat` system line, then the opponent's win or lose `DialogueScript`; the tap that dismisses the last page calls `store.finishBattle(state)` exactly once and then dismisses the cover. `battleQuit` calls `BattleEngine.forfeit` and enters `ended` with the defeat animation, so forfeit also ends in one `finishBattle` call. On `.deckExhausted` the player sees the defeat animation and the `retreat` line.

**Items in battle (M2).** Items are used only in battle from the `battleBag` button, never advance the cursor and never touch the deck: `.heal(30)` adds 30 capped at max; `.reviveOnce` sets `reviveArmed` once per battle (a second use is a no-op that still consumes the item); `.repel(steps:)` and `.directTo` are overworld effects that `useItem` ignores. Because every battle starts at full HP, potions matter only mid-battle, which keeps them from ever substituting for knowing the answer.

**Elite Four.** Four members, twelve questions each, six from each of the member's two categories through the even split of `EncounterDeck.draw` (section 2.2), due cards first within each category. Member HP follows the 0.7 rule (typical 84, so nine of twelve, matching `QuizScore.passed` for 9/12 = 75 and failing 8/12 = 67). `EliteFourRun` carries player HP across members and heals 30 percent of max between them, capped at max; an Oxygen Mask may be used once per run (M2). Losing to any member, forfeiting or leaving the screen ends the run; the next attempt starts at member one with a fresh draw. Each member win goes through `finishBattle` (a `BattleRecord` and 75 XP, also on rematches); the fourth win makes `run.isCleared` true and `finishEliteFourRun` records `eliteFourCleared`.

**Champion.** The deck is `ChampionBattle.deck`, which is `QuizEngine.makeQuiz(config: .mockExam, ...)`, so the blueprint is the real 12/12/8/7/7/8/4/2. Every correct answer deals exactly 1 to a 42-HP bar and every wrong answer deals exactly 1 to a 19-HP bar; 42 correct wins and 19 wrong loses, which is provably identical to `QuizScore.passed` because 42 + 18 = 60 and 41 + 19 = 60. The tier has `runsEveryQuestion = true`: a bar reaching zero pins at zero and the DPE says "We finish the exam, pilot. Every question counts." until all sixty are answered, so `finishQuiz(results:isMockExam: true)` receives the full mock exam. A forfeited Champion battle inserts a lost `BattleRecord` and skips `finishQuiz`, because the mock exam was not completed. `ChampionBattle.outcome(results:)` is the verdict and a test asserts it agrees with the bars for every correct count from 0 to 60. Critical and super-effective text and haptics still play on the Champion for feel; the damage stays 1.

**Battle Tower (M3).** Each floor is one battle of `BattleTower.questionsPerFloor` = 5 questions from `EncounterDeck.draw(count: 5, categories: nil, ...)` against `opponent(forFloor:)` with HP from `OpponentHP.tuned`; the player's max HP comes from the mean reviewed retention, there is no heal between floors, and miss damage is `20 + 5 * (floor - 1)`. A run ends on a loss, a forfeit or leaving the screen, and it is never persisted. `finishBattle` for tier `.tower` awards `.towerFloorCleared` 10 XP per won floor and sets `bestTowerFloor = max(bestTowerFloor, floor)`.

**Link battles (M3).** The app draws a `UInt32` seed from `SystemRandomNumberGenerator`, encodes it with `bank.version` into a seven-character code and shares it. The second player types the code into `linkCodeField` and taps `linkStart`; both fight tier `.link` against opponent id `link-<code>`, name `LINK PILOT`, nameplate `LINK`, HP from `OpponentHP.tuned` over the identical ten-question deck. `finishBattle` awards `.linkBattleFinished` 20 XP win or lose. The share text after the battle is `<code> <correct>/10 <seconds>s` and comparison is manual: no networking.

**XP.** Per answer through `submitAdventureAnswer`: `.quizAnswer(correct:difficulty:)` = 15 (+5 for difficulty 3) or 3, reason `"adventure"`. Wins through `finishBattle`: `.cloudCleared` 5, `.trainerDefeated` 25 (also the rival), `.gymBadgeEarned(firstTime: true)` 100 and 40 on a rematch, `.eliteMemberDefeated` 75, `.championCrowned(firstTime: true)` 200 and 60 later, on top of the existing `.mockExamCompleted(passed:)` 100 or 40 that `finishQuiz` awards; M3 `.towerFloorCleared` 10 and `.linkBattleFinished` 20. Losses award nothing extra; the per-answer XP stays, and every `.again` grade brought the card back sooner through `Scheduler.review`, tomorrow for a never-reviewed card.

**Badges.** `firstGymBadge` at 1 gym badge, `fourGymBadges` at 4, `allGymBadges` at 8, `eliteFourCleared`, `regionChampion`, and in M3 `towerFloor10`; all counted from `AdventureSave`.

**Companions (M3).** `CompanionStage.stage(for:)` maps novice and apprentice (reviewed retention below 0.4) to hatchling, competent and proficient (0.4 to below 0.8) to journeyman, instrumentMaster (0.8 and above) to captain. The evolution check runs when the Adventure tab appears and after every `finishBattle`, comparing `CompanionStage.stage(for: store.adventureMastery(for: category).level)` with `seenCompanionStages[category.rawValue]` (default 1) for all eight categories; a rise plays the cutscene and stores the new stage, a fall stores silently.

## 5. Retro feel spec

**Canvas.** 240 by 160 logical pixels. `IntegerScaler.scale = max(1, floor(min(viewWidth * displayScale / 240, viewHeight * displayScale / 160)))` in device pixels; an iPhone 15 at 393 points and 3x gives 1179 / 240 = 4, so the canvas is 960 by 640 device pixels, 320 by 213.33 points, centered and letterboxed in `Theme.panel`. `GBAScreen` draws the `PixelFrame` as a single `CGImage` via `Image(decorative:scale:).interpolation(.none)` at `240 * scale` by `160 * scale` device pixels. Every sprite position is an `Int`; no fractional offset ever reaches the canvas. The frame clock is `TimelineView(.animation)` quantized to 60 frames per second through the screen model's `phaseStart`, and every animation is a pure function of the frame index.

**Palette** (`Palette.entries`, index in hex; 255 is transparent): 0 ink `#0A0C0B`, 1 panel `#1A1F1C` (`Theme.panel`), 2 shade `#2E3A33`, 3 moss `#47604F`, 4 accent `#5CC78C` (the exact `AccentColor.colorset` bytes; `Theme.accent`'s 0.55 blue rounds to 0x8C, and `make-icon.swift`'s `#5cc78d` comment is off by one), 5 mint `#9FE6BC`, 6 paper `#E8F5EC`, 7 amber `#F5BA3B` (`Theme.amber`), 8 bronze `#B8791A`, 9 rust `#7A3A1E`, A danger `#E05A4E`, B airway blue `#3E6FA8`, C cloud `#8FB8E8`, D grey `#6B6F6C`, E silver `#C9CDCA`, F white `#FFFFFF`. Each sprite uses at most four indices plus transparent, like a GBA sub-palette, and a test enforces it.

**Sprites.** Text grids in `Pixel/Sprites/PlayerSprites.swift`, `LeaderSprites.swift`, `EliteSprites.swift`, `TileSprites.swift`, `UISprites.swift`, `CompanionSprites.swift` (M3). These files are rows of string literals and run well past 150 lines, so the file-length guard in M1-17 exempts `Pixel/Sprites/` by name. Battle sprites are 32 by 32 (player back sprite `player-back`, eight leaders `leader-hypoxia` ... `leader-ilsa`, four elite, `champion`); overworld tiles and walkers are 16 by 16 with two walk frames for down, up and left, right being `flippedHorizontally()`; badges, the airport marker and the cursor are 8 by 8. Placeholder silhouettes are acceptable at first; tests guard only shape and palette discipline.

**Font.** Press Start 2P, SIL Open Font License 1.1. The work item downloads the font from the Google Fonts repository, reads the shipped `OFL.txt` and the font's embedded license metadata, and bundles both under `App/Fonts/`. Point size is `8 * scale / displayScale` so glyphs sit on the pixel grid. Dialogue is authored in sentence case and rendered as written. If the download or license check fails, `RetroTheme.pixelFont` falls back to the system monospaced design and the plan continues; until the font lands, `testPixelFontIsRegistered` and `testOpenFontLicenseIsBundledAndNamesVersionOnePointOne` throw `XCTSkip` when `App/Fonts/PressStart2P-Regular.ttf` is absent, so M1-06 is green without the network and turns red only once the file exists and is not registered.

**Dialogue box.** Rows 112 to 159, full width: a 2-pixel `paper` border with a 1-pixel `ink` inner line, `panel` fill, text at logical (8, 120) and (8, 136), 28 columns by 2 rows. `Typewriter.paginate` wraps on word boundaries at 28 columns and breaks pages every 2 rows. Reveal is a cumulative frame cost per character: 2 frames each, plus 8 after `.`, `?` and `!` and 4 after `,`; holding a finger on the box costs 1 per character and skips every pause. A character is visible when its cumulative cost is at or below the frame index, which restarts at 0 for each page. When a page completes, an 8 by 8 triangle cursor at (224, 148) blinks with a 30-frame period; a tap advances and fires `Haptics.tick()`. Question stems page through the box; the answer options are SwiftUI buttons below the canvas in the pixel font on `Theme.panel`, scrollable, so FAA-length options are never truncated. No text is rasterized into a `PixelFrame`. Renderers draw frames, bars, sprites and box chrome only; every string (names, `hp/max`, dialogue) is a SwiftUI `Text` in `RetroTheme.pixelFont` positioned at `logical * scale / displayScale` points over the canvas by `GBAScreen`. Renderer tests assert pixels only.

**Region map layout (M1).** The map occupies the 30 by 14 grid of 8-pixel cells above the dialogue box. Airways are 1-pixel index B lines between cell centres, drawn first. Each airport is the 8 by 8 `airport` sprite recoloured: grey D when locked, accent 4 when badged, amber 7 for the next gym, silver E for a waypoint; a locked Elite Four or Champion airport is grey and an unlocked one amber. Transparent SwiftUI buttons sit over each airport cell at `cell * 8 * scale` points with identifier `airport-<id>`. Tapping a gym airport types its intro dialogue and shows a `Challenge` button (`gym-<gymID>`) when unlocked, or "You need the <previous badge name> first." when locked; tapping the Elite Four or Champion airport pushes `EliteFourScreen` or `ChampionScreen` when unlocked. Toolbar buttons `badgeCase` and `hallOfFame` push their screens.

**Battle layout** (logical pixels): opponent sprite at (176, 8) with `NamePlate.enemy` at (16, 16), 64 by 12; player sprite at (24, 64) with `NamePlate.player` at (144, 80), 64 by 20; dialogue box at y 112. Inside a plate at `(x, y)`: the name at `(x + 2, y + 1)` in the 8-pixel font, uppercased and at most 7 characters (`Opponent.nameplateName`, validated in content; the player plate shows `PILOT` in M1 and the companion's stage name truncated to 7 in M3); the bar at `(x + 8, y + 7)`; and on the player plate only, the numeric `hp/max` label right-aligned to end at `x + 62` on row `y + 12`. The player plate is 20 tall rather than 12 because seven name characters and a seven-character `140/140` cannot share one 64-pixel row.

**HP bars.** 48 by 4 pixels. `filledPixels = floor(hp * 48 / max)`; band `green` above 50 percent, `amber` from 20 to 50, `red` below 20, chosen from the displayed HP so the bar changes colour mid-tick. `displayedHP` steps 1 HP every 2 frames toward the target, so a 15-damage hit takes half a second, and the numeric label counts down in step. The sprite taking damage shakes with x offsets (-2, 2, -1, 1, 0) over 10 frames.

**Transitions.** `BattleWipe`: frames 0 to 15 alternate a full-screen white and ink flash every 4 frames (`Haptics.tick()` on each white frame), frames 16 to 39 close eight horizontal bands from the edges toward the centre. `BattleIntro.slideOffset` then brings the enemy in from the right (enemy x from 240 to 176) and the player from the left (player x from -32 to 24) over 12 frames, linear in integer steps. Victory: `VictoryAnimation.dropOffset` drops the opponent sprite 4 pixels per frame for 8 frames (32 total) then returns nil so it vanishes, "Gym Leader Dr. Hypoxia was defeated!" types out, `VictoryAnimation.badgeScale` grows the badge sprite from 1 to 4 over 8 frames (the sprite is blitted at that integer scale), `Haptics.correct()`. Defeat: `DefeatAnimation.fadeStep` returns 0 to 15 over 30 frames and the frame is dimmed by replacing every index with `ink` for rows where `(y + frame) % 16 < fadeStep`, "You whited out... Your misses come back sooner." types out, `Haptics.incorrect()`.

**Haptics.** `Haptics.correct()` on opponent damage, `Haptics.incorrect()` on player damage, new `Haptics.critical()` (heavy impact) on criticals and super-effective hits, new `Haptics.tick()` (selection feedback) on dialogue advance, option selection, wipe flashes and each overworld step.

**Overworld feel (M2).** Viewport 15 by 10 tiles, camera centred on the player and clamped at map edges; a step takes 8 frames; tap-to-walk draws a faint path preview along the A-star result. A tap on water, terrain, a building or an unreachable tile does nothing. Every step that lands on a cloud tile rolls a one-in-eight encounter (the 24th consecutive cloud step forces one); a triggered roll, a rival trigger or a trainer sighting clears `pendingPath` so the player stops where the event happened; all of that is one `OverworldTurn.advancing` call per step. A sighted trainer shows a "!" bubble for 20 frames, walks one tile per 8 frames along `TrainerApproach.position` until adjacent, then talks. After a cloud, trainer or rival loss the player reappears at `Respawn.placement` (the nearest visited airport's door, or the spawn) facing down, and the trainer who won is suppressed until the player leaves its sight line. Position and facing are persisted only when `pendingPath` completes, when the scene goes to the background, and immediately before a battle is presented, never per step. The D-pad overlay is four 44-point translucent buttons bottom-left, off by default, toggled from the tab toolbar and stored in a new `SettingsRecord.dpadEnabled: Bool = false` (M2-10).

**Sound.** Optional and last: six square-wave effects (select, hit, crit, hurt, badge, faint) synthesized at runtime through `AVAudioEngine` in the app, muted by default behind a new `SettingsRecord.soundEnabled: Bool = false` toggle (M3-06). No audio assets and no generator script, since any AppKit-based script (like `scripts/make-icon.swift`, which imports AppKit and CoreGraphics) is macOS-only.

## 7. Test strategy

**Linux.** `scripts/test-core.sh` (which prepends `/opt/swift/usr/bin` to `PATH` when needed and runs `swift test` in `IFRCore`) runs every `IFRCoreTests` class: the nine existing suites, every class that a Section 6 item marked Linux names (from `SourceGuardTests` through `OverworldTurnTests`, `RespawnTests`, `DirectToTests` and `RematchNoticeTests` to `LinkBattleCodeTests`), plus the extended `XPEngineTests` and `BadgeEngineTests`. That is roughly 290 tests and the whole rulebook, including both bundled JSON resources loaded through `Bundle.module` exactly as the existing bundled-bank test does. This was verified in the cloud container on 2026-09-27: `scripts/install-swift-linux.sh` installed Swift 6.0.3 and `scripts/test-core.sh` ran the nine existing suites, 54 tests, all green. The first implementation step on any machine is the same pair of commands (or Xcode's toolchain on a Mac). There is no CI today: the git repository root is `/home/user/IFR`, `FlashCards/` is a subdirectory of it, and there is no `.github` directory at that root. M1-01 adds `/home/user/IFR/.github/workflows/core-tests.yml` running `FlashCards/scripts/install-swift-linux.sh` and `FlashCards/scripts/test-core.sh` on `ubuntu-latest`; a workflow under `FlashCards/.github` would be ignored by GitHub.

**Xcode.** `scripts/test-app.sh` regenerates the project with xcodegen and runs `IFRFlashCardsTests` and `IFRFlashCardsUITests` on the iPhone 16 simulator: `AdventureStoreTests`, `PixelImageBuilderTests`, `FontBundlingTests`, `BattleScreenModelTests`, `EliteFourScreenModelTests`, `OverworldScreenModelTests`, `ChiptuneTests`, the extended `NotificationSchedulerTests` and `GameCenterServiceTests`, and the `SmokeTests` additions. Roughly 85 tests, all persistence, bundling, observation, timing or glue. App-target tests import `IFRCore` without `@testable`, and `Question` has no public initializer, so their fixtures are always `store.bank` questions. The three renderers are not here: they take only IFRCore values and produce a `PixelFrame`, so they live in IFRCore and run on Linux. Existing identifiers (`startSession`, `mcOption-0`, `grade-Good` and the rest) and tab titles are untouched because no existing screen changes.

**Determinism.** No IFRCore function calls `Date()`, `.now`, `Task.sleep` or `SystemRandomNumberGenerator`. Time enters as `now: Date` (tests use `Date(timeIntervalSince1970: 1_800_000_000)`), `answerSeconds: Double`, or a frame index; randomness enters as `inout some RandomNumberGenerator` pinned with `SeededRNG(seed: 7)`. Statistical tests use fixed seeds and generous bounds; exact-order tests assert arrays. The app injects `.now`, a `ContinuousClock` measurement and a `phaseStart` in `BattleScreenModel`, a `makeRNG` closure, and the link seed from `SystemRandomNumberGenerator`; the UI test target passes `-adventureSeed 7` so encounter tests are repeatable. `StudyStore` still uses `.now` internally, so store tests assert consequences that hold today (a wrong first answer yields `reps == 1` and `due` within two days) rather than pretending to observe tomorrow's queue.

**Thin UI.** Every screen holds one engine value (`BattleState`, `OverworldState`, `EliteFourRun`, `BattleTower`, `AdventureSave`), one phase enum and one `phaseStart`, and every user action is one engine call followed by at most one store call. Rendering is `PixelFrame` in, `CGImage` out, verified once by `PixelImageBuilderTests`. If a view needs an `if` about game rules, the condition becomes an engine property with a Linux test.

## 8. Coding rules

- New files contain zero comments: no file-path header line, no `///`, no `// MARK:`. Existing files touched (`StudyStore.swift`, `Records.swift`, `XPEngine.swift`, `BadgeEngine.swift`, `MasteryCalculator.swift`, `RootView.swift`, `NotificationScheduler.swift`, `Haptics.swift`) keep their comments, but added code has none. The no-comments guard in M1-01 enforces this for `Sources/IFRCore/Adventure`.
- Names carry meaning: transitions are present participles returning new values (`stepping`, `targeting`, `advancing(after:)`, `climbing(after:)`), predicates read as questions (`isUnlocked`, `isWalkable`, `triggers(on:)`, `isCleared`), rule namespaces are `enum`s with static functions (`Damage`, `CircuitRules`, `Pathfinder`, `Typewriter`), engines with dependencies are structs taking `Scheduler` in `init` (`EncounterDeck`), state is a `Codable, Equatable, Sendable` struct (`BattleState`, `OverworldState`, `AdventureSave`). Functions stay under 15 lines and source files under 150 lines except sprite grids under `Pixel/Sprites/`; a growing reducer branch gets its own named function. Constants are `static let` on the owning type.
- IFRCore types are value types only, all `Sendable`; content and state are `Codable`; no classes. `IFRCore.Category` is always fully qualified in tests.
- Layout: `IFRCore/Sources/IFRCore/Adventure/{Battle,Encounters,Content,Circuit,Pixel,Pixel/Sprites,Overworld,Companions,Tower,Link}`, one type per file except tiny enums that belong together; tests are `<Type>Tests.swift` in `IFRCore/Tests/IFRCoreTests`; app code in `App/Screens/Adventure/`, `App/Theme/RetroTheme.swift`, `App/Fonts/`, `App/Audio/`; records in `Records.swift`; store methods in `StudyStore.swift`.
- Tests: `final class <Type>Tests: XCTestCase`, private factories at the top, one behaviour per test, names that read as sentences and are unique across the project, short rationale messages only where the assertion is not self-evident, `accuracy:` for floating comparisons, `XCTAssertThrowsError` then `$0 as? AdventureContentError == .case` for validation.
- Content JSON is loaded through `AdventureContent.load()`, which always validates; `validate()` throws the first `AdventureContentError` in a fixed order mirroring `QuestionBank.validate()`; the bundled file is loaded by a test on every run; every id, dialogue reference, sprite id, category, warp and door must resolve, nameplates must fit, and dialogue pages must fit the box. A content change is a test run, not a code review.
- Learning integrity is enforced in code: the only way to record an answer is `store.submitAdventureAnswer`, which uses `Grade(mcCorrect:)` and the private `applyReview`; `BattleTurnResult.grade` is asserted in engine tests; `ItemEffect` is a closed enum; decks come only from `StudyQueue.session`, `QuizEngine.makeQuiz` and `QuizConfig.mockExam`; grep guards fail the build otherwise.
- Every new `StudyStore` accessor reads `_ = revision` and every mutation ends with `revision += 1`. Overworld movement never writes the store per step. Never reuse the XP reason `"dailyGoal"`. Never persist a `CardStateRecord` with `reps == 0`.
- No SpriteKit, no swift-fsrs, no third-party packages. Notification and leaderboard identifiers are `static let` strings or static functions beside the existing ones.

## 9. Risks, open questions and what to cut first

**Risks, highest first.** (1) SwiftUI `Canvas` blurring scaled images: M1-06 runs before any screen, has a screenshot done criterion and a `Path`-rectangle fallback behind `SpriteRasterizer`. (2) Learning-integrity drift as features grow: everything routes through `submitAdventureAnswer`, `applyReview` stays private, and the grep guards plus the grade-mapping comparison test in M1-11b catch bypasses. (3) `awardBadges` scans all `ReviewRecord`s per answer (docs/BACKLOG.md); Adventure adds no scans because badge fields come from `AdventureSave`, but a 60-question Champion still triggers sixty scans. Acceptable now; the backlog fix is independent. (4) Per-draw HP tuning is exact for six and eight correct, but seven correct wins 67 percent of subsets without crits and 119 of 120 with one crit; the one losing subset misses every difficulty-3 question, which is the run that deserved to lose, and the exhaustive tests state this honestly. (5) Human Factors has 16 MC-capable questions, so gym one repeats quickly; retention weighting keeps the repeats useful and the pool-size content test blocks a `questionCount` above the pool. (6) Press Start 2P at 8 pixels is hard to read for long explanations; explanations page through the box and the `Source` button opens the full `SourceSheet`. (7) Two container declarations must stay in sync; the store tests catch the test list and the first app launch catches the app list. (8) `goalMetToday` requires `dueCount == 0`, so a lost battle that makes cards due can defer the daily goal; that is the existing Study behaviour and it is pedagogically right. (9) Font license: verified from the downloaded `OFL.txt` before bundling, with the monospaced fallback if anything is unclear. (10) The coverage-aware `reviewedRetention` with a ten-card minimum means a player who wins gym one with exactly ten reviewed cards sits right at the threshold; the numbers are tunable constants with tests, not rules.

**Open questions, decided provisionally so work can start.** Adventure answers count as quiz days for `quizzes10/50` (yes, `inQuiz: true`). Rematches pay per-answer XP (yes, same path) and a 40 XP badge bonus without duplicating the badge. The Champion always runs all sixty questions even after a certain fail (yes, so the mock exam is complete and every answer is a review), and a forfeited Champion run is a lost battle that never reaches `finishQuiz`. Elite Four losses restart from member one (yes). The Battle Tower leaderboard needs App Store Connect setup before M3 ships (yes, the only external dependency). Adventure consumes the Study tab's new-card allowance (yes, a card introduced in a battle really was introduced).

**Cut order if time runs short.** M3-06 chiptune; M3-05 link battles; M3-04 Battle Tower and its leaderboard; M2-07 rival; the D-pad half of M2-10; M2-06 items; companion art reduced to stage 1 with palette swaps; Elite Four sprites as recoloured leaders; the M3-02 evolution cutscene (the sprite still changes silently); and finally the whole overworld, because the gym circuit on the region map is a complete, shippable game at the end of Milestone 1. Never cut: the review path through `StudyStore`, the content validation tests, the integer-scaled canvas, the typewriter box and the ticking HP bars; those are the learning integrity and the retro feel the mode stands on.
